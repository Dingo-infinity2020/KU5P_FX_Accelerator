# RFSoC 数据源与 KU5P 接口评估

日期：2026-10-27。状态：本地工程的静态核对与容量推导，尚未进行本轮硬件测试。

后续范围更新：用户确认两台 RFSoC、合计 16 路，且已补充并核对 100 MS/s 工程。最新接入与计算预算见 [双 RFSoC 方案](dual-rfsoc-plan.md)；本文保留单台八路 320 MS/s 数据源的核对记录。

本文只记录接口结论与设计影响。RFSoC 原始工程、RTL/BSV、BD/XDC、软件源码、XSA、位流及生成目录保留在仓库外，不上传 GitHub。后续可同步自行编写的摘要与派生程序，不能把复制或改名的原始工程当作派生程序入库。

## 1. 这次补齐的输入事实

证据来自提供的 `sync_daq_320MSps_iq` 工程，已交叉核对工程配置、块设计连接、数据打包逻辑和嵌入式控制程序。这里描述该份工程配置，不代表现场设备一定运行同一固件。

| 项目 | 本地工程证据 | 对 KU5P 的意义 |
|---|---|---|
| 器件 | XCZU47DR-FFVE1156-2-I | 已有具体 RFSoC 器件信息；板卡型号/版本另行确认 |
| 工具链 | Vivado/Vitis 2025.2 | 与 KU5P 的 Vivado 2026.1 分开管理，不自动迁移源工程 |
| 输入数 | 8 路复数信号流，4 个 ADC tile 各两路 | I/Q 分量不各算一路 |
| ADC 与抽取 | ADC 配置 3.84 GS/s，抽取 12 | 输出每路 320 MS/s 复数采样 |
| 数据容器 | I、Q 各 16 位；两组复数样本/160 MHz 拍 | 一个复数样本 4 字节；16 位容器不等于 16 位有效精度 |
| 数据出口 | PL CMAC 100GbE，Ethernet/IPv4/UDP | 需要接收大 UDP 报文并按通道与计数重排 |
| 控制出口 | PS 上的 SFP/RJ45 千兆网络，UDP 控制端口 3000 | 控制网络与 100GbE 采样流分别设计 |
| F 部分 | 主采样路径未见科学频道化 PFB/FFT | RFDC 内已有 DDC/抽取滤波，KU5P 的频道化功能仍需规划 |

**每路有效科学带宽 100 MHz 的需求保持不变。** 320 MS/s 是当前工程的数据速率；实际选取的频段、通带平坦度和抗混叠指标尚需确认。

## 2. 数据路径与接收格式

当前路径为：RFDC 的 I/Q 输出 → I/Q 合并 → PPS 控制的八路门控 → 每路 64 到 512 位宽转换及跨时钟 FIFO → 每路打包、按包轮询合并 → 100GbE。

| 层次 | 从源码推导的长度/内容 |
|---|---|
| 单个 UDP 用户数据 | 32 字节元数据 + 8192 字节采样数据，共 8224 字节 |
| 元数据 | 格式标识、通道号、数据类型、该通道的 64 位包计数和校验标识 |
| 单包样本 | 一路的 2048 个复数样本；320 MS/s 时覆盖名义 6.4 µs |
| IPv4/UDP 长度 | IPv4 总长 8252 字节；UDP 长度 8232 字节 |
| 打包器 AXI 输出 | 130 个完整 64 字节拍，共 8320 字节，不含 MAC 后加的 FCS |

长度和布局属于静态推导，尚缺真实抓包核对。该帧大于标准 1500 字节 MTU，链路中各接收/转发环节必须容纳它。

打包器尾拍的 `TKEEP` 全有效，因此比 Ethernet 头加 IP 数据报多出 54 字节填充。接收端应依据 IP/UDP 长度确定有效数据边界，不能将整个 Ethernet 尾部继续解释成采样数据。`TKEEP` 表示字节有效性，参考 [AMD PG203 的 AXI 接口说明](https://docs.amd.com/api/khub/documents/PW98UL_o1JrXVALl1mZhBw/content)。

由合并与打包逻辑推导，采样区候选解释为小端的 `I0,Q0,I1,Q1,...`，每分量 16 位。需用已知正负数、单音和已知相位记录确认符号、时间顺序、幅度标度与边带方向后，才能冻结解析契约。

## 3. 时间与同步还缺什么证明

工程已有四 tile MTS、SYSREF 门控、NCO 相位复位、GPS/外部 PPS 选择和按 PPS 开始发送的逻辑，因此同步机制已不再是完全未知项。MTS 返回、实际延迟与相位重复性仍须形成可追溯记录。官方同步流程同时涉及分频器、FIFO 延迟和数字功能事件，见 [AMD PG269 Synchronization Steps](https://docs.amd.com/r/en-US/pg269-rf-data-converter/Synchronization-Steps)。

当前采样包不包含绝对采样时间、会话号、配置版本、每样本有效标志或完整溢出信息。包计数在打包阶段递增，不能单凭计数连续就证明前级样本从未丢失或重复。

在“同一次启动、八路同一首样本、上游连续且未静默丢样”验证后，才能用 `包计数 × 2048 + 包内索引` 建立各路相对样本编号。绝对时间还需把共同起点绑定到明确 PPS/纪元；网络到达顺序不能替代采样时间。

必须补查的两个具体条件：

- 门控逻辑使用不断更新的快照寄存器，接收与发送规则独立；在输入有效信号有空洞或下游反压时，存在覆盖/重复样本的风险。需要计数测试流证明样本守恒，目前未实测确认故障。
- PPS 等待模块超时后仍可改变 SYSREF 门控输出，软件主要打印状态。超时不能作为成功同步证据；采集会话需要明确的同步有效状态。

## 4. 控制协议不能直接照旧 README 实现

当前 `QueryReply` 结构在八路时按目标平台自然对齐推导为 **336 字节**，文档中的 328 字节属于旧布局。增加的 `boot_mode` 和 `uptime_s` 改变了后续偏移；采样率/位宽/IQ 模式分别位于 64/68/72，四组统计数组从 80 开始。

该结论来自头文件字段与发送 `sizeof` 的源码核对，没有本轮在线回包证据。未来解析器应核对长度及版本，遇到未知布局明确拒绝，不能依靠同一个常量格式标识猜测。

`SetMixer` 使用 MHz/角度参数，固件给 NCO 的频率取负，`GetMixer` 回读时再翻回主机约定。需保留这套符号并用已知单音/互相关相位验证，不能在 KU5P 侧再随意取一次共轭。同步更新与非同步更新也要区分，见 [AMD PG269 Multi-Tile Mode](https://docs.amd.com/r/en-US/pg269-rf-data-converter/Multi-Tile-Mode)。

## 5. 容量与 FFT 基线的修订

原始采样净速率为 `8 × 320e6 × 2 × 16 = 81.92 Gb/s = 10.24 GB/s`。在上述包长、无 VLAN、加 4 字节 FCS、8 字节前导/SFD 与平均 12 字节 IFG 的假设下，名义占用约 83.44 Gb/s；这不是实测持续吞吐或 PHY 编码/RS-FEC 后的串行线速。单包轮询、ARP、拥塞与缓存余量需单独验证。

8 路每路每秒约 156250 包，合计 125 万包/秒。完整原始流不能持续经 KU5P 的 PCIe Gen3×8 原样转发到主机；该接口即使只扣编码，上限也约 7.88 GB/s，低于 10.24 GB/s。主目标应是板上计算并读出积分结果，不能默认主机接收全量原始流。

| 计算配置 | 512 点格点间隔 | H=N 的帧推进 | 约 1 s 对应 M | 全频道 36 项 X 更新率 |
|---|---:|---:|---:|---:|
| 直接处理 320 MS/s | 625 kHz | 1.6 µs | 625000 | 11.52 G 次/秒 |
| 候选：滤波后抽取 2 至 160 MS/s | 312.5 kHz | 3.2 µs | 312500 | 5.76 G 次/秒 |

首版“512 点、M 可配、默认约 1 s”的方向保留。100/125 MS/s 的旧预算继续作为算例，不能当作这份工程的实际输出。320 MS/s 直接做 512 点时，科学频谱细度也随之变化，尚需评估是否适用。

表中的 X 更新率按保留全部频道计算。若只相关有效 100 MHz 对应的 K 个频道，应使用 `36 × K × f_s/N`：320 MS/s、512 点、理想选取约 160 个频道时约为 3.6 G 次/秒。实际边缘频道由滤波响应决定；频谱格点仍为 625 kHz，前级接收与全速 FFT 的负荷也仍在。

可比较完整 320 MS/s 处理、KU5P 接收后先滤波抽取、或后续调整 RFSoC 输出配置。抽取必须有满足 100 MHz 有效带宽指标的抗混叠滤波；160 MS/s 只是候选，尚未选定。将 320 变成 100 MS/s 是 5/16 有理重采样，也不能只靠丢弃样本实现。

## 6. 下一阶段的证据顺序

1. 建立独立协议解析与短记录回放：长度、元数据、I/Q 顺序、坏包/重复/乱序处理都能核验。
2. 获取已知计数样本和同源信号记录，验证八路共同起点、停止/重启边界、反压下的样本连续性与相位重复性。
3. 比较 320 MS/s 与带限抽取路线的滤波、F/X 吞吐、存储和频谱效果，再确定计算采样率。
4. 结合 KU5P 厂家可重建源工程确定 100GbE 接收框架、GT/参考时钟、模块与 FEC 配置。RFSoC 已有 CMAC 不代表 KU5P 收端已经可用。
5. 首先以两路可重放输入验证 512 点计算核心，再扩展八路和实际接口。

本轮未执行原工程脚本、构建、驱动安装、网络控制、烧录或上板操作。已有 RFSoC 历史实现报告是有用证据，但正时序裕量不能替代 CDC、样本连续性或科学正确性的验收。
